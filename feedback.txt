Issues/opportunities to fix:
Prisma schema mismatch: In the checked-in generated Prisma client (inline schema), I only see WaitlistEntry, Profile, LoginLog, Subscription. However several routes use prisma.migrationBatch, prisma.migrationResult, and prisma.monthlyUsage. If your deployed Prisma client does include these models, great — but the repo snapshot here doesn’t. Either:
Commit the full prisma/schema.prisma (with MigrationBatch, MigrationResult, MonthlyUsage, etc.) and re‑generate client, or
For tables not represented in Prisma, keep using prisma.$queryRaw/$executeRaw (like you did for support_tickets), and remove typed model calls that would 500 at runtime.
Middleware naming: the file shown is proxy.ts exporting function proxy and config. Next.js middleware must export default function middleware in middleware.ts (at project root). If you already have middleware.ts elsewhere importing proxy and re‑exporting default, you’re good. If not, protected dashboard redirects may not fire.
Stripe API version: "2026-01-28.clover" looks like a forward/fantasy version. Pin to a current, valid date to avoid webhook/SDK mismatches.
Anthropic model IDs (claude‑haiku‑4‑20250414, claude‑sonnet‑4‑20250514) also look future‑dated. Use currently available model IDs and keep the graceful fallback you already have.
Rate limiting uses an in‑memory Map. On serverless this resets per instance and doesn’t cluster. Consider Upstash/KV/Redis if you keep it post‑hackathon.
RLS: you enabled RLS on profiles and waitlist_entries. Support tickets use raw inserts; if you later expose reads to users, add appropriate policies (admin-only or user‑scoped) in Supabase.
